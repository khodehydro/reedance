# قرارداد بین‌سکویی محتوای Reedance — نسخهٔ ۱

> **وضعیت: مشخصات طراحی؛ پیاده‌سازی هنوز انجام نشده است.** این متن مرجع هنجاری (normative) برای `contracts/v1/*.schema.json`، خروجی ویندوز و ورودی اندروید است. واژه‌های «باید» و «رد شود» الزام v1 هستند. در تعارض با توضیح‌های آزادِ README، این سند و schemaها مقدم‌اند. تغییر ناسازگار، نسخهٔ جدید `v2` می‌خواهد؛ از تغییر بی‌صدا در v1 خودداری کنید.

## ۱. سه نوع فایل و مرز اعتماد

| نام | سازنده → مصرف‌کننده | داده‌ها | اعتماد |
| --- | --- | --- | --- |
| `.rddraft.json` | ایجنت محتوا → Electron | **یک JSON خام** از متن آهنگ و درسِ تولیدشده: سطرهای **بدون زمان**، ترجمه/توکن، لغت/معنی/مثال، گرامر/افعال/جداول، جمله/اصطلاح و آزمون؛ **بدون صوت/کاور/مسیر رسانه/کلید** | ورودی نامطمئن و قابل‌ویرایش؛ نه بستهٔ قابل انتشار. |
| `.rdpack` | Electron → هاست → Kotlin | یک فایل باینری: هدر کوچک + **یک ZIP کامل رمزنگاری‌شده** شامل `lesson.json` **زمان‌دار** و صوت **انتخاب‌شده در ویندوز** و کاور اختیاری + GCM tag | فقط پس از تأیید manifest امضاشده، هش، GCM و schema نصب شود. |
| `latest.json` | Electron → هاست → Kotlin | envelope JSON حاوی payload بایتی Base64URL و امضای Ed25519 | عمومی و قابل کش؛ **درس/صوت داخل آن نیست**. `payload` نشانی/هش/نسخهٔ `.rdpack` را می‌بندد. |

فایل خام با [`draft.schema.json`](../../contracts/v1/draft.schema.json)، `lesson.json` نهایی **فقط بعد از انتخاب صوت و سینک تایم‌لاین** با [`lesson.schema.json`](../../contracts/v1/lesson.schema.json)، `latest.json` با [`manifest-envelope.schema.json`](../../contracts/v1/manifest-envelope.schema.json) و payloadِ بازشده با [`manifest-payload.schema.json`](../../contracts/v1/manifest-payload.schema.json) سنجیده شوند. schema پیش‌نویس برای انواع لغت/گرامر/سؤال به `$defs` شمای درس با ID `urn:reedance:lesson:v1` ارجاع می‌دهد؛ validator باید هر دو schema محلی را register کند، بدون fetch شبکه. JSONها UTF-8 (بدون BOM)، بدون نام کلید تکراری، بدون `NaN`/`Infinity` و با سقف اندازهٔ بخش ۳ هستند. schema شرط‌های **ساختاری** را پوشش می‌دهد؛ قواعد مرجع متقابل/زمان‌بندی/حقوق اینجا و در اعتبارسنج Windows/Android اعمال شوند.

```
متن آهنگ → ایجنت → quiet-step.rddraft.json   (فقط درس، خطوط بی‌زمان)
                                      ↓ import در Windows Studio
اپراتور → انتخاب audio.* از سیستم → waveform/تایم‌لاین اختصاصی
                                      ↓ ثبت شروعِ همهٔ سطرها + اصلاح/تأیید
                         lesson.json زمان‌دار + صوت محلی + [کاور]
                                      ↓ ZIP → AES-256-GCM
                              یک فایل .rdpack
                                      + latest.json (Ed25519؛ فقط metadata)
                                      ↓ هاست HTTPS → Android آفلاین پس از نصب
```

**مرز مسئولیت:** فایل خامِ ایجنت **نمی‌تواند** `startMs/endMs`، `media`، صوت یا کاور داشته باشد؛ Windows تنها مرجع اضافه‌کردن رسانه و زمان‌هاست. ZIP فقط **داخل بستهٔ نهایی** قرار می‌گیرد و JSON خام ZIP نیست. نسخهٔ قدیمیِ `.rddraft` به‌شکل ZIP در این قرارداد پذیرفته نمی‌شود؛ این اصلاح پیش از ساخت دو برنامه انجام شده و نیازمند مهاجرتِ محتوای منتشرشده نیست.

## ۲. هویت، نسخه و سازگاری

- `songId`: شناسهٔ slug سراسریِ یکتای **یک آهنگ با یک زبان مقصد**؛ پس از انتشار عوض نشود. انتشار یک اثر با دو زبان مقصد به‌عنوان دو دورهٔ مستقل، `songId` جدا می‌خواهد. `targetLanguage` در v1 فقط `en`، `es` یا `ko` و برای آن شناسه تغییرناپذیر است. `locale` برای تلفظ، مثل `en-GB`/`es-ES`/`ko-KR` است و باید با پیشوند زبان مقصد آغاز شود.
- `contentVersionCode`: عدد صحیح مثبت و صعودی برای هر `songId`، دامنهٔ ۱ تا `2147483647`؛ نسخهٔ صادرشده **هرگز دوباره استفاده نمی‌شود**. `displayVersion` الگوی `major.minor.patch` فقط نمایشی است؛ ترتیب به‌روزرسانی فقط با `contentVersionCode`. ویرایش فایل قبلی، بازنشر با همان شماره، یا عقب‌بردن شماره ممنوع؛ بازگشت به محتوای پیشین با بسته‌ای تازه و **شمارهٔ بالاتر** انجام شود.
- `draftSchemaVersion`، `lesson.schemaVersion`، `manifestVersion` و `containerVersion` هرکدام مستقل و در v1 برابر ۱ هستند؛ شمارهٔ APK جداست. کلاینت نسخهٔ schema/container ناشناخته را با پیام «برای باز کردن، برنامه را به‌روز کنید» رد می‌کند و نصب قبلی را نگه می‌دارد. یک schema قدیمیِ نصب‌شده با update اپ، همچنان باید قابل خواندن بماند یا با migration صریح پشتیبانی شود.
- تطبیق الزامی پس از بازگشایی: شناسهٔ `songId` و `targetLanguage` در bootstrap، manifest، `lesson.json` و مسیر محلی یکسان باشند؛ `package.encryptionKeyId` با header، `package.sizeBytes` با طول واقعی و `package.sha256` با SHA-256 تمام بایت‌های `.rdpack` برابر باشد. شاخص `lesson.schemaVersion` نیز با `lessonSchemaVersion` manifest برابر باشد.
- یک URL ثابت HTTPS برای `latest.json` هر آهنگ در کاتالوگ bootstrapِ APK. فایل بسته فقط در همان مسیر پایهٔ manifest و با `fileName` ساده از manifest امضاشده قرار می‌گیرد. مسیر نسخه‌دار فایل بسته immutable است؛ جایگزینی فقط روی `latest.json`.

### امضای `latest.json`؛ بدون ابهامِ canonical JSON

Envelope دقیقاً این سه کلید را دارد: `signatureKeyId`، `payload`، `signature`. هر دو مقدار دوم Base64URL **بدون `=`**، بدون فاصله و با کدگذاری کمینه هستند. `payload` پس از decode، **بایت‌های اصلی UTF-8ِ JSON** است؛ هرگز برای اعتبارسنجی امضا آن را دوباره serialize نکنید. الگوریتم امضا **Ed25519 خالص** است، نه Ed25519ph یا ECDSA.

```
message = UTF8("REEDANCE-MANIFEST-V1\n")
        || UTF8(signatureKeyId) || UTF8("\n") || decodedPayloadBytes
signature = Ed25519.sign(publisherPrivateKey, message)   // 64 bytes
```

مجموعهٔ کلید عمومی پین‌شدهٔ APK با `signatureKeyId` انتخاب می‌شود؛ کلید عمومی برای هر ID دقیقاً **۳۲ بایت raw Ed25519 (RFC 8032)** است (در Node می‌توان آن را با wrapper استاندارد SPKI وارد کرد). **ابتدا** امضای بایت‌های payload بررسی و **بعد** payload parse و با schema/شناسه‌ها بررسی شود. شناسهٔ کلید نیز چون بخشی از `message` است امضا شده است. envelope و payload با JSON parser سخت‌گیر دارای ردِ کلید تکراری parse شوند؛ padding یا Base64URL غیراستاندارد، کلید ناشناخته، فیلد ناشناخته و payload بیش از ۱۶ KiB رد شوند. نمونهٔ تولید/مصرف فقط در `contracts/v1/fixtures/` تستی است و کلیدهای آن برای انتشار ممنوع‌اند.

`package.fileName` باید با `v${contentVersionCode.toString().padStart(6, '0')}-${sha256}.rdpack` دقیقاً برابر باشد (`sha256`، هگز lowercase). نشانی بسته از resolve کردن **همین basename** نسبت به URL manifest ساخته شود. فقط HTTPS؛ origin باید برابر originِ manifest و در allowlist ازپیش‌ثبت‌شدهٔ اپ باشد، هیچ userinfo/query/fragment یا redirect به host دیگری پذیرفته نشود. در درخواست manifest نیز redirect به origin نامجاز رد شود. URL موجود در `latest.json` به‌صورت arbitrary URL پشتیبانی نمی‌شود؛ تغییر دامنه به APK/سیاست امضاشدهٔ جدید نیاز دارد.

برای ضد rollback محلی، کلاینت بزرگ‌ترین `(contentVersionCode, sha256)` معتبرِ دیده‌شده برای هر آهنگ را پایدار نگه می‌دارد؛ نسخهٔ پایین‌تر و **همان شماره با هش متفاوت** را رد می‌کند. برای اولین نصب، هاست می‌تواند manifest قدیمیِ دارای امضای معتبر را replay کند؛ **بدون سرویس آنلاینِ مستقل یا زمان قابل‌اعتماد، تضمین تازگی مطلق ممکن نیست**. کلاینت با نسخهٔ نصب‌شدهٔ قدیمیِ معتبر در حالت آفلاین کار می‌کند. اگر manifest تازه روی host زودتر از pack قرار گیرد، آپدیت شکست می‌خورد، نه نسخهٔ قبلی.

## ۳. فایل باینری `.rdpack` — layout دقیق

تمام اعداد چندبایتی در هدر **unsigned big-endian**؛ واحد طول **بایت**. هیچ padding، metadata یا ساختار دیگری در انتهای فایل نباشد. `keyId` صرفاً شناسهٔ عمومی انتخاب کلید متقارن است؛ خود کلید در فایل/manifest نیست.

| offset | طول | مقدار |
| --- | ---: | --- |
| `0..7` | ۸ | ASCII `RDPACK1` (۷ بایت) و سپس بایت صفر `0x00`؛ magic دقیق `RDPACK1\0` برای container v1 |
| `8` | ۱ | `L` = طول `keyId`، ۱ تا ۳۲ |
| `9..8+L` | `L` | ASCII `keyId` مطابق `^enc-[a-z0-9-]+$` |
| `9+L..20+L` | ۱۲ | nonce تصادفیِ ۹۶ بیتی، از CSPRNG، یکتا برای هر export با همان کلید |
| `21+L..28+L` | ۸ | طول ZIP plaintext به‌صورت uint64 big-endian؛ در v1 باید ≤ حد مجاز باشد |
| `29+L..28+L+P` | `P` | ciphertext با AES-256-GCM بر ZIP plaintext، `P` = طول همان ZIP |
| `29+L+P..44+L+P` | ۱۶ | tag احراز اصالت GCM |

بنابراین `header = bytes[0 .. 29+L)`؛ `AAD = header` **بدون هیچ تبدیل یا اضافه**؛ خروجیِ رمز `ciphertext || tag` و `totalFileLength = 45 + L + P`. کلید ۳۲ بایت و nonce ۱۲ بایت؛ tag ۱۶ بایت؛ هیچ salt/KDF در v1 وجود ندارد. برای هر خروجی **nonce تازه با CSPRNG** بگیرید حتی اگر محتوای درس یکسان است؛ هرگز nonce را زیر یک کلید دوباره استفاده نکنید. روی ویندوز export به temp و rename پس از اتمام؛ failure مجوز استفادهٔ مجدد از nonce قبلی برای خروجی دیگری نیست. روی Android قبل از استفاده از دادهٔ بازشده، پایان decrypt و صحت tag را بررسی کنید؛ در decrypt جریانی، خروجی تا دریافت tag **غیرقابل‌اعتماد** است.

### ZIP plaintext فقط برای بستهٔ نهایی

`ZIP` استانداردِ تک‌دیسک با نام فایل ASCII در root، **بدون پوشه، symlink، ZIP64، ورودی رمزدار، فایل اجرایی/اسکریپت و entry تکراری**؛ روش فشرده‌سازی فقط `STORE(0)` یا `DEFLATE(8)`؛ ترجیح `STORE` برای صوتِ ازقبل‌فشرده و `DEFLATE` برای JSON. در v1 فقط پرچم UTF-8 (bit 11) مجاز است؛ extra field، comment و data descriptor (bit 3) نباید وجود داشته باشند؛ CRC/طول/نام ورودیِ local و central directory باید منطبق باشند. صادرکنندهٔ ویندوز باید ZIP را به‌شکلی بسازد که این شرط‌ها را رعایت کند، حتی اگر کتابخانهٔ پیش‌فرضِ ZIP فیلد اضافه یا descriptor می‌نویسد. ورودی‌های دقیقِ بستهٔ منتشرشده: `lesson.json`، دقیقاً یک `audio.mp3`/`audio.m4a`/`audio.wav`، و صفر یا یک `cover.jpg`/`cover.png`/`cover.webp`، بدون فایل دیگر. `media.audio.path` و `media.cover.path` درس باید دقیقاً به همین نام‌ها اشاره کنند؛ `sha256` هر رسانه با بایت‌های ورودی ZIP برابر و MIME ادعاشده با امضای فایل/decoder سازگار باشد. صوت باید با Media3 آفلاین قابل پخش و duration اعلام‌شده نزدیک duration واقعی باشد (اختلاف ≤۱۰۰۰ ms؛ برای metadata متغیر encoder با بررسی انسانی قابل تنظیم). متن JSON و تصاویر/صوت متعلق به هم و به آهنگ مشخص باشند.

پیش‌نویس **ZIP نیست**: `.rddraft.json` بدون رسانه/ثانیه را Windows فقط به‌عنوان دادهٔ نامطمئن import می‌کند؛ کد/اسکریپتِ سازنده در `tools/content-cli/` جداست و داخل Electron اجرا نمی‌شود. ویرایش‌ها در snapshot پروژه و سپس درس نهایی نوشته می‌شوند؛ صادرکردن مستقیم بایت‌های raw draft ممنوع است. صوت انتخاب‌شدهٔ محلی هنگام export با نام استاندارد `audio.*` به ZIP نهایی اضافه می‌شود؛ `lesson.json` زمان‌ها، `durationMs`، MIME و hash همان بایت‌ها را دارد.

**محدودیت مشترک پیش از استخراج:** فایل `.rddraft.json` و `lesson.json` هرکدام ≤۴ MiB؛ `latest.json` ≤۳۲ KiB و payload بازشده ≤۱۶ KiB؛ صوت انتخاب‌شده ≤۲۴۰ MiB، کاور انتخاب‌شده ≤۸ MiB، ZIP plaintext و `.rdpack` هرکدام ≤۲۵۶ MiB؛ حداکثر ۳ entry در ZIP نهایی و مجموعِ اندازهٔ خروجی extract ≤۲۵۲ MiB. ZIP bomb، compression ratio غیرعادی (>۱۰۰:۱ برای هر entry غیر JSON)، طول/CRC اشتباه، مسیرهای `..`/`/`/`\\`/نام با تغییر case، data descriptor مبهم، archive چندبخشی یا extra field غیرمجاز رد شود. decoder تصویر/صوت در sandbox/محیط محدود و با سقف حافظه اجرا شود. برای audio طولانی‌تر از این سقف، **قبل از انتشار سقف را با نسخهٔ قرارداد جدید و اپ سازگار تغییر دهید**؛ نباید بی‌صدا بخشی از صوت را جداگانه منتشر کرد.

## ۴. ورودیِ ایجنت: JSON خام، بدون صوت و زمان

قرارداد ساختاریِ [`.rddraft.json`](../../contracts/v1/draft.schema.json) فقط **یک فایل UTF-8** است؛ نمونهٔ معتبر و قابل import در [`fixtures/quiet-step.rddraft.json`](../../contracts/v1/fixtures/quiet-step.rddraft.json) قرار دارد. مدیر متن آهنگ را به ایجنت می‌دهد؛ ایجنت از روی همان متن، هر سطر را با `id/text/translationFa/translationEn/tokens` و بدون `startMs/endMs` می‌نویسد و آرایه‌های `vocabulary` (lemma، معنی، مثال/افعال)، `grammar` (توضیح، جدول، check)، `idioms`، `sentences`، `vocabularyTables` و `questions` را تکمیل می‌کند. عنوان، زبان مقصد، locale و منبعِ ادعاییِ lyrics/lesson در همین فایل‌اند؛ هنرمند و سطح اگر در raw معلوم باشند ثبت می‌شوند، وگرنه Windows پیش از export تکمیلشان می‌کند. **هیچ `media`، فایل صوتی، کاور، path صوت، hash صوت، کلید یا URL انتشار در draft نیست.** فیلدهای اضافی از جمله زمان پیشنهادی و صوتِ Base64 رد شوند؛ اگر محتوایی نامطمئن است به‌جای ساخت دادهٔ دروغ، `sources.*.rightsStatus = "unverified"` باقی بماند.

Windows پس از importِ معتبر، پروژهٔ مستقل ایجاد می‌کند. اپراتور از File Picker فایل MP3/M4A/WAV را از **سیستم خود** انتخاب می‌کند؛ برنامه آن را در پروژه کپی/نسخه‌برداری می‌کند تا حذف/تغییر فایل مبدأ پس از import خروجی را بی‌صدا عوض نکند، codec/MIME/duration/hash را می‌سنجد و waveform می‌سازد. کاور اختیاری نیز در Windows انتخاب/اعتبارسنجی می‌شود. از انتخاب صوت، **هیچ sync خودکارِ قطعی** فرض نشود: کاربر سطرهای بی‌زمان را روی تایم‌لاین با playhead، علامت‌گذاری، drag یا زمان‌نویسیِ عددی به میلی‌ثانیه می‌چسباند، پیش‌نمایش همزمان صدا/متن ویرایش می‌کند و تک‌تک سطرها را تأیید می‌کند. اگر ابزار تراز خودکار افزوده شد فقط پیشنهاد است.

تبدیل به `lesson.json` نهایی **عمل Windows** است: همان IDها و داده‌های آموزشی پس از اصلاح حفظ می‌شوند؛ `schemaVersion: 1`، `media.audio.{path,mimeType,durationMs,sha256}`، `credits.audio` و `lyrics[].startMs` به آن افزوده می‌شوند (`endMs` اختیاری)، و metadata ایجنت مانند `generator/sources/createdAt` در رکورد داخلی پروژه می‌ماند، نه در فایل مصرفی Android. انتخاب‌نشدن صوت، باقی‌ماندن حتی **یک سطر بدون زمان معتبر**، نامعتبرشدن زمان‌ها پس از عوض‌کردن صوت، مرجع سؤال/سطرِ شکسته، نبود مدرک حقوق یا تأیید نهایی، همگی باید export را **مسدود** کنند. تعویض صوت همهٔ زمان‌ها را «نیازمند بازبینی» می‌کند؛ تغییر متن/تقسیم سطر، همان سطر و ارجاعات آموزشی را نیازمند بررسی دوباره می‌کند. نشان‌گذاری‌های قبلی می‌توانند به‌عنوان پیشنهاد در پروژه بمانند، اما خودکار معتبر تلقی نشوند. وضعیت و پیشرفت ویرایش در DB محلی ذخیره می‌شوند؛ خامِ واردشده قابل بازتولید/ردیابی است.

## ۵. `lesson.json` منتشرشده؛ مدل دادهٔ آموزشی

Schema کامل در [`contracts/v1/lesson.schema.json`](../../contracts/v1/lesson.schema.json) است. نمونهٔ **بعد از انتخاب صوت و هم‌زمان‌سازی آزمایشی** در [`fixtures/lesson.json`](../../contracts/v1/fixtures/lesson.json) قرار دارد. فیلدهای هسته‌ای:

```json
{
  "schemaVersion": 1,
  "songId": "quiet-step",
  "targetLanguage": "en",
  "locale": "en-GB",
  "title": "Quiet Step",
  "artist": "Reedance Originals",
  "level": "A1",
  "media": { "audio": { "path": "audio.wav", "mimeType": "audio/wav", "durationMs": 4000, "sha256": "..." } },
  "lyrics": [{ "id": "line-1", "startMs": 0, "text": "One quiet step.", "translationFa": "یک قدم آرام.", "translationEn": "One quiet step.", "tokens": [{ "surface": "quiet", "translationFa": "آرام", "translationEn": "calm", "lexemeId": "en:quiet" }] }],
  "vocabulary": [{ "lexemeId": "en:quiet", "lemma": "quiet", "normalizedKey": "quiet", "translationFa": "آرام", "translationEn": "calm", "example": { "text": "A quiet room.", "translationFa": "اتاقی آرام.", "translationEn": "A calm room." } }],
  "grammar": [], "idioms": [], "sentences": [], "vocabularyTables": [], "questions": []
}
```

این قطعه **نمایش ساختار** است (هش `...` و بخش‌های خالی/ناتمام آن نمونهٔ قابل استفاده نیست). برای import در ویندوز از fixture خامِ `quiet-step.rddraft.json` و برای آزمون بستهٔ منتشرشده از `fixtures/lesson.json` و `.rdpack` استفاده کنید. قرارداد شامل شناسه‌های پایدارِ `line`، `lexeme`، `grammar`، `idiom`، `sentence` و `question` است. جدول‌های آموزش `columns` و `rows` هستند؛ `grid` فقط یک آسان‌نویس CLI است. هیچ HTML/JS/CSS در درس مجاز نیست؛ رشته‌ها همیشه با text renderer نمایش داده شوند، نه `innerHTML`/WebView injection. `tone` از مجموعهٔ محدود رنگ‌ها برای تنوع کارت است و به جنسیت/صحت دلالت نمی‌کند.

اعتبارسنج معنایی علاوه بر JSON Schema **باید** حداقل اینها را کنترل کند:

1. تمام IDهای هر نوع در همان آهنگ یکتا؛ `lexemeId` در `vocabulary` یکتا و در کل کتابخانه به یک `(targetLanguage, normalizedKey)` ثابت نگاشت شود. `normalizedKey` یک کلید lemma ویرایشگر-تأییدشده در NFC/lowercase است، نه شکل صرف‌شده؛ برای `sí` و `si` تمایز حفظ شود. چند معنی/نقش می‌تواند `lexemeId` جدا و همان normalizedKey داشته باشد؛ گزارش واژگان غیرتکراری آن را یک‌بار می‌شمارد. تغییر نگاشت یک ID باید خطا دهد، نه این‌که کارت قبلی بی‌صدا معنای دیگر بگیرد.
2. زمان‌های `lyrics.startMs` صعودی، بدون تکرار، در بازهٔ `0 ≤ startMs < durationMs` و هر `endMs` (اگر هست) > start و ≤ duration. توکن‌های هر خط باید به ترتیب با متن و معنی‌ها سازگار باشند؛ ابزار می‌تواند هشدار دهد، انسان تأیید کند. `lineId` سؤال/جمله باید موجود، `lexemeId` هر توکن یا سؤال باید در واژگان همان بسته تعریف‌شده باشد. `conceptId` گرامر می‌تواند در چند آهنگ مشترک باشد.
3. هر جدول حداقل یک سرستون و سطر و تعداد خانهٔ هر `row` مساوی تعداد `columns`؛ متن خام یا سلول دوزبانه `{fa,en,dir?,locale?}`. عرض/تعداد محدود؛ رابط RTL/LTR را درست اعمال کند.
4. انواع سؤال فقط `choice`، `match`، `order` و `typing`. `choice.correctId` در options باشد و options ID یکتا؛ `match` pairها ID یکتا و ترتیب نمایشی اگر داده شده دقیقاً permutation آنهاست؛ `order` از ترتیب آرایهٔ chunks جواب می‌گیرد و اگر `presentationOrder` دارد permutation همان IDs است؛ `typing.accepted` بدون تکرار پس از normalization و شامل پاسخ صحیح. نرمال‌سازی پاسخ تایپی: Unicode NFC، trim، lowercasing طبق locale زبان مقصد، حذف نشانه‌های انتهایی `. ! ? , …` و مقایسهٔ دقیق؛ accent/حروف کره‌ای حفظ شوند، مترادف‌ها صریحاً در `accepted` بیایند. هر سؤال حداقل یک توضیح فارسی/انگلیسی و ارتباط واژگان مرتبط در صورت استفاده از لایتنر دارد.
5. `idAliases` فقط برای مهاجرت **یک‌به‌یکِ معناییِ تأییدشده** از شناسهٔ قدیمِ نسخهٔ پیشین به شناسهٔ موجود در نسخهٔ جدید، در همان زبان/نوع؛ `from != to`، بدون چرخه، بدون مبدأ/مقصد تکراری و با بازبینی انسان. برای حذف، پیشرفت آرشیو شود. نسخه‌های قبلی در Windows با نسخهٔ جدید مقایسه شوند؛ IDs تغییرکرده و لایتنر/نشان‌ها هشدار و تأیید صریح بگیرند. نتیجهٔ آزمون با `versionCode` قبلی تاریخچه است؛ با پاسخ اصلاح‌شده بدون شرکتِ دوباره به‌عنوان نتیجهٔ نسخهٔ فعلی نمایش داده نشود.
6. قبل از تأیید، اطلاعات منابع و مجوز صوتِ **انتخاب‌شده در ویندوز**، متنِ داده‌شده به ایجنت، کاورِ اختیاری، اجازهٔ دانلود آفلاین و اعتبارها بررسی شوند؛ `*.rddraft.json` صرفاً **ادعای منبع متن/درس** است، نه سند حقوق صوت و نه مجوز قانونی. محتوای مشهور دموی وب بدون مدرک وارد خروجی نشود.

## ۶. انتشار، دانلود، مدیریت کلید

**ترتیب انتشار:** در ویندوز از snapshotِ approved خروجی بگیر؛ کلید `encryptionKeyId` شناخته‌شدهٔ Android را انتخاب کن؛ ZIP + `.rdpack` را بساز و SHA-256 و طول را ثبت کن؛ payload manifest را بر مبنای آن تولید و امضا کن؛ `.rdpack` را روی هاستِ HTTPS در مسیر immutable آپلود و از راه دور طول/هش آن را بررسی کن؛ **در آخر** `latest.json` را آپلود/جایگزین کن. `Cache-Control` پیشنهادی: package `public, max-age=31536000, immutable`؛ manifest `public, max-age=60, must-revalidate` با ETag. پاکسازی CDN و rollbackِ manifest با شمارهٔ پایین‌تر باعث مسئلهٔ سازگاری است؛ اصلاح با نسخهٔ بالاتر.

**دانلود/نصب اندروید:** manifest را بخوان و امضا/دامنه/نسخه را تأیید کن؛ اگر offline است از فایل نصب‌شده استفاده کن؛ برای نسخهٔ جدید، `.part` را در فضای خصوصی و با WorkManager دریافت کن (resume فقط با ETag/Content-Range معتبر، وگرنه restart)؛ هم اندازه/هش و هم سرآیند/AAD/GCM را بسنج؛ ZIP را فقط در staging با محدودیت استخراج باز کن؛ درس/صوت/کاور/schema/ارجاعات/مدت را تأیید کن؛ سپس پوشهٔ نسخه‌دار را در همان volume تثبیت و با transactionِ DB نشانگر «نسخهٔ فعال» را تغییر بده. اجرای Media3 و UI تا تثبیت نسخهٔ جدید از نسخهٔ قبلی است. در crash recovery، پوشهٔ ناقص/یتیم را پاک و به نشانگر نسخهٔ معتبر بازگرد؛ نسخهٔ قبلی را پس از تأیید استفاده‌نشدن پاک کن. بعد از نصب، اصل بستهٔ رمزنگاری‌شده را می‌توان برای صرفه‌جویی فضا حذف کرد، اما درس/صوتِ بازشده در storage خصوصی می‌ماند؛ این تصمیم باید در UI میزان فضا را روشن کند.

**کلیدهای تولید:** کلید متقارن ۳۲بایتی AES با `encryptionKeyId` مشخص، در Windows operator به‌شکل محافظت‌شده ذخیره و به **build اندرویدِ تولید** از مسیر امن secret injection تزریق می‌شود؛ در repo/installer عمومی/manifest/draft نباشد. کلید خصوصی Ed25519 فقط نزد ناشر، ذخیره با رمز و backup جدا؛ کلید عمومی Ed25519 با `signatureKeyId` در APK پین است. `keyId`ها صرفاً ID هستند. اگر کلید توزیع تعویض شود، اول APK سازگار با کلید تازه را منتشر/رواج دهید، **بعد** بسته با keyId تازه؛ کلاینت قدیمی آپدیت را رد و نسخهٔ آفلاین قبلی را حفظ می‌کند. کلید امضای جدید نیز اول در APK پین شود. رخنهٔ private signing key در APK قدیمی با هاست عمومی قابل جبران فوری نیست و به برنامه/فرایند پاسخ امنیتی نیاز دارد.

**محدودیت امنیتی:** رمزنگاری فایلِ توزیعی مانع نگاه اتفاقی به فایل می‌شود، اما به‌دلیل نیاز به رمزگشایی آفلاین روی دستگاه کاربر، کلید در APK/حافظه قابل استخراج است؛ **DRM، محافظت مطلق از صوت، خرید اشتراک یا لغو قطعی دسترسی نیست**. امضای ناشر مستقل از کلید AES است. استودیو و Android هر دو باید خطاهای کلید/امضا/فرمت را از «مشکل شبکه» تمیز دهند و هیچ محتوای تأییدنشده‌ای را نمایش ندهند.

## ۷. نمونهٔ آزمون مشترک و تغییر قرارداد

`contracts/v1/fixtures/` دارای نمونهٔ کوچک و صرفاً تستیِ **پیش‌نویس بی‌صوت/بی‌زمان** `quiet-step.rddraft.json`، فایل صوتیِ جداگانهٔ `audio.wav` برای انتخاب فرضی در ویندوز، `lesson.json` زمان‌دارِ حاصل از دو علامت تایم‌لاین، `.rdpack`، `latest.json`، کلید عمومی امضا و **کلید AES تستیِ آشکار** است. کلید تست را هرگز در release APK/Windows استفاده نکنید. ویندوز باید اول فایل خام را **بدون نیاز به صوت** وارد کند، سپس WAVِ جدا را از File Picker انتخاب و دو سطر را در `0 ms` و `2000 ms` روی تایم‌لاین سینک کند و فقط پس از آن با کلیدهای تست بسته‌ای مستقل بسازد؛ Android fixture و خروجی مستقل ویندوز را رمزگشایی و محتوای درس/زمان/سؤال را دقیق بخواند. یک وکتورِ دارای nonce/tag/امضای تغییرکرده نیز باید رد شود. فاز صفر شامل تثبیت fixture و تست سازگاری است؛ اگر schema/معنای فیلدی عوض شد، fixture و هر دو تست با PR واحد تغییر کنند یا `contracts/v2` بسازید.
