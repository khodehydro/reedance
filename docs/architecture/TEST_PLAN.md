# آزمون و دروازهٔ تحویل مشترک

هدف این سند: دو ایجنتِ مستقل نتوانند هرکدام «بستهٔ درستِ خودشان» بسازند ولی فایل واقعیِ ویندوز در اندروید باز نشود. **قرارداد v1** در [PACKAGE_V1.md](PACKAGE_V1.md) و schemaها در [`contracts/v1`](../../contracts/v1/) است؛ تست صرفاً JSON Schema کافی نیست. وضعیت فعلی مخزن: نمونهٔ وب، specification و fixture تست؛ اجرای تست‌های وب (`npm test`, `npm run build`) اثباتِ کارکرد Android/Electron نیست.

## دروازهٔ صفر: تعامل‌پذیری قبل از رابط کاربری

1. `fixtures/quiet-step.rddraft.json` را در ویندوز **بدون انتخاب صوت** وارد کنید؛ در raw هیچ `media` و هیچ `startMs/endMs` نباشد و export در این وضعیت ممنوع باشد. شمای draft و شمای lesson منتشرشده متفاوت‌اند، ولی تعریفِ لغت/گرامر/سؤال را مشترک دارند. parser با UTF-8، سقف اندازه و ردِ کلید تکراری/JSON مخرب تست شود؛ raw مجوز حقوقی نیست.
2. مدیر WAVِ fixture را **جداگانه از سیستم** انتخاب کند؛ waveform را ببیند، دو سطر را در `0 ms` و `2000 ms` با تایم‌لاین ثبت و preview کند. Windows فقط پس از بازبینی/حقوق/تکمیل همهٔ سطرها با کلیدهای **صرفاً تست** `lesson.json` زمان‌دار و `.rdpack` مستقل صادر/verify کند؛ گزارش SHA-256، طول، header/AAD، Ed25519 signature و hash صوت بدهد. Android همان bytes را از fake HTTPS server بگیرد و درس/صوت/زمان/سؤال را بررسی کند. برای **خروجی تازهٔ Windows** nonce از CSPRNG؛ fixture golden ثابت فقط برای آزمون قابل تکرار است.
3. **بدون تبدیل دستی** یا patch مخصوص fixture در Android، یک خروجی جدیدِ Windows (با nonce تازه، همان schema) وارد و پخش شود. سپس همان نسخهٔ آهنگ را با `contentVersionCode + 1` صادر کن؛ به‌روزرسانی را روی دستگاه و در حالت آفلاین بعد از نصب بررسی کن. همین تبادل تکرارشونده در CI/گزارش acceptance لازم است.
4. خروجی انحرافیِ هر سمت باید به **خطای مشخص و حفظ نسخهٔ قبلی** منجر شود، نه crash یا رندر نصفه. اگر schema یا فرمت بایت تغییر کرد، هر دو تیم و fixture در یک تغییر هماهنگ یا `contracts/v2` پیش بروند.

## آزمون‌های معنایی مشخصِ محصول

- **تایم‌لاین اختصاصی ویندوز:** انتخاب صوت از file picker، پخش/مکث/seek/loop و waveform، ثبت start هر سطر با playhead/کلید میان‌بر، drag/ویرایش عددی در مقیاس میلی‌ثانیه، highlight همزمان متن و صدا، undo/redo و ذخیرهٔ markها پس از restart. حالت خامِ بی‌صوت، حالت صوتِ انتخاب‌شده با سطرِ بی‌زمان و حالتِ صوتِ تعویض‌شده هر سه **نباید** خروجی بدهند. `lesson.json` منتشرشده باید همان audio hash و markerهای تأییدشده را داشته باشد.
- **آزمون مستقل:** ورود پلیر را مکث کند و محتوا فقط از `questions` بسته باشد؛ choice، match (در غلط فقط pairهای غلط)، order و typing با مقایسهٔ NFC/locale/نشانهٔ انتهایی؛ بازخورد فارسی/انگلیسی، نمره و خروج/بازگشت درست. روزانهٔ لایتنر با دادهٔ نصب‌شده تولید شود، نه سؤال کد وب.
- **جدول و دسترس‌پذیری:** ستون‌ها/screen reader، اسکرول افقیِ خود جدول در عرض کوچک، RTL فارسی/LTR انگلیسی، accent اسپانیایی/Hangul، theme dark، اندازهٔ نوشته و reduced motion. رنگ ملایم کارت به‌تنهایی معنی گرامر یا جواب صحیح نیست.
- **آمار خروجی‌های ویندوز:** فهرست تمام نسخه‌های صادرشده با زبان، هش، حجم، تاریخ، انتشار و missing؛ شمارهای default/latest-exported/all-version با label واضح، export CSV/JSON و هش مبنای گزارش. حذف فایل از دیسک و rescan باید هشدار بدهد؛ آمار منتشرشدهٔ ناقص را بی‌سروصدا بازشماری نکند.
- **حقوق و امنیت:** برای هر فایل صوتی/متن/تصویر سند permissionِ توزیع و دانلود آفلاین، تأیید انسانی و متن اعتبار؛ استفاده از آهنگ/کاور مشهور وب بدون مجوز تست شکست انتشار است. کلیدهای واقعی خارج Git/آرتیفکت عمومی/لاگ؛ backup رمزدار + آزمایش بازیابی؛ rotationِ keyId با rollout Android.

## مرز انتشار نهایی

«آمادهٔ عرضه» فقط وقتی اعلام شود که روی Windows واقعی installer، **import JSON خام بدون صوت، انتخاب جداگانهٔ آهنگ، سینک تمام لیریک روی تایم‌لاین** و export انجام شده باشد؛ `.rdpack` خروجی در Android واقعی **بدون اینترنت پس از نصب** کار کند؛ `v1→v2` با همان `manifestUrl` و حفظ پیشرفت آزمایش شده باشد؛ URL/کلید/مجوز واقعی و فایل‌ها روی HTTPS موجود باشند. قبل از آن، تحویل **معماری/fixture/نسخهٔ آزمایشی** است، نه دو برنامهٔ نهایی. نمونهٔ وب و تست‌هایش به‌تنهایی هیچ‌یک از این شرط‌ها را تأمین نمی‌کنند.
